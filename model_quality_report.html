HiggsLM — Model Quality & Training Correctness Report

Review of the architecture, training loop, and data/eval pipeline for issues affecting trained-model quality · June 12, 2026

Executive summary

The core components are in good shape: the Muon+AdamW optimizer is a faithful, well-engineered implementation (fused compiled steps, Polar Express orthogonalization, cautious weight decay), GQA with QK-norm and a learnable per-head temperature is sound, and the parameter routing (matrices → Muon; embeddings, head, gains/biases → AdamW) follows Muon best practice. However, a learning-rate scheduling bug silently erases the separate Muon learning rate, the RMSNorm layers have a spurious bias initialized to 1, and the evaluation pipeline is broken by an int16 token-dtype overflow. Several smaller issues compound these. Findings are ordered by expected impact on the quality of the trained LLM.

Critical findings

Critical

1. The LR schedule clobbers the Muon learning rate — --matrix_lr has no effect

scripts/pre_train.py:223–232 
for group in optimizer.param_groups:
    group["lr"] = group["lr"] * lr        # (a) multiplies an absolute LR by an absolute LR
    if group['kind'] == 'muon':
        group["momentum"] = muon_momentum

for param_group in optimizer.param_groups:
    param_group["lr"] = lr                # (b) then overwrites EVERY group with the same value

Why it matters: Two stacked bugs. Loop (a) is wrong on its own — get_lr() returns an absolute learning rate (e.g. 3e-4), so multiplying it into group["lr"] every step would compound it away to ~0 within a few steps. Loop (b) then makes (a) dead code by assigning the same scheduled LR to all groups — including the Muon groups you configured with --matrix_lr 1e-4. From step 2 onward, Muon and AdamW run on an identical schedule peaking at max_lr, and the matrix LR you sweep on the command line changes nothing. Muon updates are orthogonalized (roughly unit spectral norm), so their correct LR scale is genuinely different from AdamW's; losing independent control of it directly costs final loss.

Fix: Store each group's base LR once at construction and scale by the schedule ratio:

for group in optimizer.param_groups:
    group.setdefault("base_lr", group["lr"])      # do once, before training
...
sched = get_lr(epoch, args.warmup_steps, args.max_lr, args.epochs, args.min_lr) / args.max_lr
for group in optimizer.param_groups:
    group["lr"] = group["base_lr"] * sched
    if group["kind"] == "muon":
        group["momentum"] = muon_momentum
Critical

2. RMSNorm has an additive bias — initialized to ones

llm/gpt.py:10–17 also train.py:59–60 
self.g = nn.Parameter(torch.ones(input_shape))
self.b = nn.Parameter(torch.ones(input_shape))   # bias initialized to 1, not 0
...
output = (output * self.g) + self.b

Why it matters: RMSNorm by definition has no additive bias (that's the point of dropping LayerNorm's mean-centering). Worse, the bias here starts at +1, so at initialization every normalized activation entering attention, the MLPs, and the final LM head is shifted by a constant +1 in every channel. That injects a large common-mode component into Q/K/V projections and the output logits at step 0, distorts the carefully scaled 0.02-std init, and the network must spend early training un-learning it. It also interacts badly with finding #5 (weight decay pulls g and b toward 0 — and a decayed gain shrinks the whole residual stream).

Fix: Remove self.b entirely (standard RMSNorm), or at minimum initialize it with torch.zeros(input_shape). Note this is duplicated in train.py.

Critical

3. Eval tokenizer casts token IDs to int16 — overflow and a hard crash

verified by running
llm/tokenizer.py:20–22 consumed by llm/engine.py:7,17 → eval_manager.py 
def str_to_pre_train_tokens(prompt):
    tokens = tokenize_prompt(prompt)                          # uint16 numpy
    return torch.tensor(tokens, dtype=torch.int16).unsqueeze(0)

Why it matters: GPT-2 token IDs go up to 50,256 but torch.int16 maxes out at 32,767. I verified both failure modes against your installed torch 2.10: (a) the uint16→int16 reinterpretation wraps high IDs to negative numbers (e.g. 50256 → -15280), and (b) nn.Embedding rejects ShortTensor indices outright ("Expected ... Long, Int; but got torch.ShortTensor"). So every HellaSwag evaluation triggered from the training loop either crashes or — if the dtype were "fixed" to a wrapping cast — silently evaluates on corrupted token sequences. You currently have no trustworthy benchmark signal during pre-training.

Fix: return torch.tensor(tokens, dtype=torch.long).unsqueeze(0) (and tokenize_prompt can stay uint16 on disk, but anything entering the model should be long/int32).

4. Float hyperparameters declared type=int — overrides crash or silently truncate

verified by running
scripts/pre_train.py:26–47, 63–68, 94 
parser.add_argument("--learning_rate", type=int, default=3e-4, ...)
parser.add_argument("--lr",            type=int, default=3e-4, ...)
parser.add_argument("--max_lr",        type=int, default=3e-4, ...)
parser.add_argument("--min_lr",        type=int, default=3e-5, ...)
parser.add_argument("--weight_decay",  type=int, default=0.01, ...)
parser.add_argument("--matrix_lr",     type=int, default=1e-4, ...)

Why it matters: argparse only applies type to command-line strings, so the float defaults pass through fine — which hides the bug. But the moment you try to tune: --learning_rate 3e-4 exits with "invalid int value: '3e-4'" (verified), and --min_lr 0.00003 fails the same way. Any value that does parse as an int (e.g. --weight_decay 1) is accepted with a truncated meaning. In practice every LR/weight-decay sweep is either impossible or wrong, which matters enormously given findings #1 and #7.

Fix: type=float on all six arguments.

High

5. Weight decay applied to RMSNorm gains/biases and the attention α temperature

scripts/pre_train.py:176–181 
hidden_gains_biases = [p for p in model.blocks.parameters() if p.ndim < 2]
...
dict(kind="adamw", params=hidden_gains_biases, lr=args.learning_rate,
     betas=(0.9, 0.95), weight_decay=args.weight_decay, eps=1e-10)

Why it matters: The 1-D parameter group contains the RMSNorm gains g, the (spurious) biases b, linear-layer biases, and the per-head QK-norm temperature alpha — and decays all of them toward zero. Decaying a norm gain toward 0 shrinks the entire residual stream; decaying alpha toward 0 flattens the attention distribution toward uniform, fighting the QK-norm design. Standard practice (and your own legacy train.py:218–221, which gets this right) is weight_decay=0.0 for all sub-2-D parameters.

Fix: Set weight_decay=0.0 for the hidden_gains_biases group. Decaying the embedding/head matrices is a defensible choice either way.

High

6. MLP down-projection missing the depth-scaled residual init

llm/gpt.py:128–140, 204–213 
class MLP(nn.Module):
    def __init__(self, embed_dim):
        ...
        self.scale_init = 1     # <- wrong attribute name, on the wrong module: a no-op
...
def _init_weights(self, module):
    std = 0.02
    if hasattr(module, "GPT_SCALE_INIT"):   # only attention's c_proj has this flag
        std *= (2 * self.num_blocks) ** -0.5

Why it matters: The GPT-2 scheme scales the init of both residual-path output projections (attention c_proj and the MLP's second linear) by (2·num_blocks)-0.5 so residual-stream variance stays controlled with depth. Here only the attention projection gets the flag; self.scale_init = 1 on the MLP module is dead code — the init hook checks for an attribute named GPT_SCALE_INIT on the nn.Linear itself. The MLP down-projection (the larger contributor, 4× fan-in) is initialized 4× "too hot", inflating activations at init and making early training noisier than intended.

Fix: Replace nn.Sequential with named layers and tag the down-projection: self.down_proj.GPT_SCALE_INIT = 1 (and delete self.scale_init).

High

7. LR is updated after optimizer.step() — first step runs at full base LR

scripts/pre_train.py:213–232 
optimizer.step()                 # step 0 uses the constructor LRs: 3e-4 / 1e-4
...
lr = get_lr(epoch, ...)          # warmup value for THIS step, applied to the NEXT one

Why it matters: With 750 warmup steps, step 0 should run at max_lr/750 ≈ 4e-7. Instead the very first update — when gradients are at their largest and Muon's orthogonalized update has full spectral magnitude — executes at the peak LR of 3e-4. A single hot first step can meaningfully perturb the init (this is exactly the regime warmup exists for), and the whole schedule stays shifted by one step thereafter. The same after-step pattern also means muon_momentum warmup (0.85→0.95) never applies its first value.

Fix: Move the LR/momentum assignment to the top of the epoch loop (before optimizer.step()), computing it from the current epoch.

8. Validation loss is stale for 99 of every 100 logged steps

scripts/pre_train.py:234–256 
if epoch % 100 == 0:
    with torch.no_grad():
        ...
        val_loss = loss(...)         # computed every 100 steps

if (args.wandb == True):
    wandb.log({ ..., "val/loss": val_loss.item(), ... })   # logged EVERY step

Why it matters: The wandb val/loss and val/perplexity curves (and the per-step console print) repeat a 100-step-old value 99% of the time, drawn from a single batch. Your validation signal — the thing you'd use to detect overfitting, LR problems, or divergence — is both stale and extremely noisy. Since findings #1/#7 are LR bugs, this is precisely the instrumentation that would have caught them.

Fix: Log val/loss only on the steps it's computed (pass step=epoch to wandb.log so curves align), and average over ~20+ val batches with the model in eval() mode. Reset the val dataloader each time so the metric is comparable across evals.

Medium

9. Generation never crops the context — crashes once prompt + generated > seq_length

llm/engine.py:14–25 guard at llm/gpt.py:96–99 
for _ in range(max_tokens):
    logits = model(tokens)              # tokens grows by 1 each iteration, never cropped
    next_token = torch.argmax(...)      # greedy decoding
    tokens = torch.cat((tokens, next_token), dim=1)

Why it matters: GroupedQueryAttention.forward raises ValueError when T > seq_length, so any eval prompt longer than seq_length - max_tokens (5-shot HellaSwag prompts are long) kills the benchmark — and since evals run inside the training process, it kills the training run at step 1000. Greedy argmax decoding is also a poor default for generative benchmarks. The same uncropped loop exists in scripts/chat_pre_train.py:83–87.

Fix: Feed the model tokens[:, -model.seq_length:] each iteration (and wrap the in-loop eval in a try/except so a failed benchmark can't abort training).

Medium

10. Dataloader starts every shard at position B·T — the first batch of each shard is never trained on

llm/dataloader.py:30–47 same in train.py:39–53 
def reset(self):
    self.current_shard = 0
    self.tokens = load_tokens(self.shards[self.current_shard])
    self.current_position = self.B * self.T     # should be 0 for single-process

Why it matters: This offset is a leftover from the multi-GPU nanoGPT loader, where position starts at B*T*process_rank. With a single process it should be 0; as written you skip the first B*T tokens of every shard (and of the val shard), and the tail-end wraparound geometry is slightly off. Small data loss, but free to fix.

Fix: self.current_position = 0 in both reset() and the shard-advance branch.

Medium

11. Gradient clipping at max_norm = 5.0 is loose enough to be a no-op

scripts/pre_train.py:212

Why it matters: The standard for this model family is 1.0 (GPT-2/3, nanoGPT). At 5.0 the clip will essentially never engage except during a full-blown spike, so it provides little of the stability benefit clipping is there for — particularly relevant while warmup is broken (#7).

Fix: clip_grad_norm_(model.parameters(), 1.0), and keep logging train/gradient_norm (already done) to confirm where clipping engages.

Medium

13. Duplicate LR flags: training uses --learning_rate, wandb logs --lr

scripts/pre_train.py:26–41, 116, 179–181

Why it matters: Not a naming nit — an experiment-integrity bug. The param groups are built from args.learning_rate, but the wandb config records args.lr. Both default to 3e-4, so today they happen to agree; the first time you change one, every wandb run's recorded learning rate is wrong, and cross-run comparisons (the scientific purpose of this repo) become misleading. Note also that after finding #1, the LR that actually matters is args.max_lr, a third flag.

Fix: Delete --lr, derive max_lr from --learning_rate (or make peak LR the single source of truth), and log vars(args) wholesale so config and reality can't diverge.

14. get_weight_decay references undefined globals — will crash when enabled

llm/lr.py:19–20 
def get_weight_decay(it):
    return weight_decay_scaled * (1 - it / num_iterations)   # neither name exists

Why it matters: The call site in pre_train.py:221 is commented out behind a TODO; the moment that TODO is completed the run dies with NameError on step 0 — or worse, gets "fixed" hastily mid-experiment. It's imported at the top of pre_train.py, so it looks ready to use.

Performance & portability findings

Low / Perf

15. load_tokens: int32 targets crash CE on CPU, and .astype defeats mmap_mode

verified by running
llm/dataloader.py:8–10 
def load_tokens(filename):
    npt = np.load(filename, mmap_mode="r").astype(np.int32)
    return torch.from_numpy(npt)

Why it matters: Two separate things. (a) .astype materializes the entire ~200MB shard into RAM immediately, so the mmap_mode="r" buys nothing. (b) int32 targets into nn.CrossEntropyLoss work on MPS (verified) and on current CUDA, but crash on CPU with "expected scalar type Long but found Int" (verified on your torch 2.10) — so the same script silently isn't portable across the three devices it auto-selects between.

Fix: Keep the mmap and convert per-batch instead: return the uint16 mmap, then in next_batch do x = torch.from_numpy(buf[:-1].astype(np.int64)).view(B, T) (a B·T-sized copy, not a shard-sized one). Targets as int64 are safe everywhere.

Low / Perf

16. wandb.watch(model, log="all", log_freq=100) adds real overhead

scripts/pre_train.py:160

Why it matters: log="all" hooks every parameter and gradient and serializes histograms for ~195M parameters every 100 steps — noticeable step-time spikes and large uploads, and the hooks can interact poorly with torch.compile. You already log the one number that matters (train/gradient_norm).

Fix: Drop wandb.watch, or use log="gradients" with log_freq=1000 if you want occasional histograms.

18. Legacy train.py — the path the README documents — round-trips loss through the CPU

train.py:230–253 cli.py:16, README.md:33 
x, y = x.to(device), y.to("cpu")
output = model(x).to("cpu")        # full (B,T,50304) logits copied to CPU every micro-step
train_loss = loss_fn(...)          # loss + part of backward computed on CPU

Why it matters: This file appears to be the predecessor of scripts/pre_train.py, but it's what cli.py train-cli and the README invoke. Each micro-step copies a ~400MB logits tensor to the CPU and runs the cross-entropy (and its backward) there — a massive, device-sync-laden slowdown. It also duplicates the RMSNorm-bias bug (#2), runs a val forward every step, accepts a dropout argument that's wired to nothing, and references the global device inside the model class. If it's dead, it's a trap: anyone (including future-you) following the README trains the wrong, slower, buggier model.

Fix: Point cli.py/README at scripts/pre_train.py and delete train.py, or at minimum remove the .to("cpu") round-trip.

Low

19. Checkpoints store _orig_mod.-prefixed keys from the compiled module

llm/checkpoint_manager.py:14 scripts/pre_train.py:165–168

Why it matters: model.state_dict() on a torch.compiled model prefixes every key with _orig_mod.. chat_pre_train.py happens to work because it compiles before loading, but any consumer that doesn't compile first (eval scripts, weight conversion, sharing the checkpoint) will fail to load. Scientific-setup considerations (not bugs)

Note

Token budget vs. model size

Defaults train ~195M parameters (51.5M embedding + 51.5M untied head + ~92M blocks) for 19,083 steps × 8 grad-accum × 8 batch × 1024 tokens ≈ 1.25B tokens — about 6 tokens/param, vs. the ~20 tokens/param compute-optimal point (~4B tokens for this size). If wall-clock allows, more steps (or a smaller model at the same budget) should produce a measurably better model. The effective batch of 65K tokens/step is also on the small side for a 3e-4 peak LR; if you grow the batch, grow the LR with it.

Note

No weight tying between embedding and LM head

The legacy train.py:144 ties lm_linear.weight = embedding.weight; the active llm/gpt.py does not. Untied is a legitimate modern choice, but at this scale the head is 26% of all parameters — tying would let you reinvest ~51M params into depth/width at the same memory cost. Whichever you choose, make it deliberate and note it in the experiment config (it currently differs between the two model definitions in the repo). Also, the untied head's init of std 0.02 produces a reasonable initial loss (≈ ln 50304 ≈ 10.8), so no action needed there.

Note

What looks right (for confidence)

  • Optimizer: the fused Muon/AdamW implementation is correct and careful — Nesterov momentum via lerp, Polar Express coefficients with the tall/wide matrix branch, factored second moment, cautious weight decay, 0-D CPU tensors to dodge recompiles, and the max(1, rows/cols)0.5 LR scaling.
  • Parameter routing: embeddings, head, and 1-D params to AdamW; block matrices to Muon, grouped by shape for stacking — exactly per Muon guidance.
  • Attention: GQA dimensions are consistent; QK-norm with the learnable per-head α correctly cancels SDPA's internal 1/√d so logits are α·(q̂·k̂); RoPE is applied consistently (interleaved pairing on both q and k; rotation commutes with the α scaling, so the order is fine); is_causal=True with enable_gqa=True is correct.
  • Loss/accumulation: per-micro-step loss division by grad_accum_steps, detached accumulation for logging, clipping before the step — all correct. bf16 autocast with fp32 RoPE caches is a good precision arrangement.
  • Vocab padding to 50304 (divisible by 128) is the standard throughput trick and harmless.
