Critical int16 token overflow — silent data corruption llm/tokenizer.py:22
Correctness

str_to_pre_train_tokens creates a tensor with dtype=torch.int16. The GPT-2 tokenizer has a vocabulary of 50,257 tokens, but int16 can only represent values up to 32,767. Any token with ID ≥ 32,768 silently wraps to a negative number. This corrupts roughly 35% of the vocabulary for every eval prompt, producing garbage outputs that have nothing to do with model quality. 

# WRONG — int16 max is 32767, vocab goes to 50256
return torch.tensor(tokens, dtype=torch.int16).unsqueeze(0)
Fix
# Use int32 or let PyTorch infer (defaults to int64)
return torch.tensor(tokens, dtype=torch.int32).unsqueeze(0)
Critical Learning rate double-application and full override scripts/pre_train.py:220–229
Correctness Training Dynamics

The training loop applies the LR schedule in two back-to-back loops that conflict with each other. The first loop multiplies the existing group LR by the absolute schedule value (not a multiplier), then the second loop immediately overwrites every group — including Muon groups — with the same flat value. The result: the Muon optimizer always receives the AdamW learning rate, and the carefully crafted per-group LRs set during optimizer construction are discarded every epoch. 

# Loop 1: multiplies lr by itself (lr is an absolute value, not a ratio)
for group in optimizer.param_groups:
    group["lr"] = group["lr"] * lr          # wrong scale
    if group['kind'] == 'muon':
        group["momentum"] = muon_momentum

# Loop 2: overwrites ALL groups (including muon) with the same scalar
for param_group in optimizer.param_groups:
    param_group["lr"] = lr                  # destroys Muon LR
Fix
# Single loop, scale each group's base LR independently
lr_scale = get_lr(epoch, args.warmup_steps, args.max_lr, args.epochs, args.min_lr) / args.max_lr

for group in optimizer.param_groups:
    group["lr"] = group["base_lr"] * lr_scale  # stored at init
    if group['kind'] == 'muon':
        group["momentum"] = muon_momentum

Store base_lr on each group when building param_groups so the scale factor can be applied without losing the original per-group rate.

High No CUDA synchronization before timing — measurements are meaningless scripts/pre_train.py:195–211
Metrics Profiling

CUDA kernels execute asynchronously. time.perf_counter() records wall-clock time on the CPU, which returns before the GPU has finished. The reported elapsed_time (and everything derived from it logged to W&B) measures only CPU dispatch overhead, not actual GPU compute time — typically off by 10–50×. 

start_time = time.perf_counter()      # CPU time only
for micro_step in range(args.grad_accum_steps):
    ...
    train_loss.backward()
end_time = time.perf_counter()         # GPU still running
Fix
if device == "cuda": torch.cuda.synchronize()
start_time = time.perf_counter()

for micro_step in range(args.grad_accum_steps):
    ...
    train_loss.backward()

if device == "cuda": torch.cuda.synchronize()
end_time = time.perf_counter()
High No KV-cache — inference is O(T²) per token llm/engine.py · llm/gpt.py:54
Speed VRAM

generate_pre_train calls model(tokens) with the full growing token sequence on every step. At token n the model re-processes all n previous tokens from scratch. For the 100-token eval prompts used in HellaSwag, this means ~5,050 full attention operations instead of 100. The GroupedQueryAttention class even has a TODO: Add KV-cache comment acknowledging this. 

# engine.py:19-22 — reprocesses entire context every step
for _ in range(max_tokens):
    logits = model(tokens)              # full forward pass
    next_token = torch.argmax(logits[:, -1, :], dim=-1, keepdim=True)
    tokens = torch.cat((tokens, next_token), dim=1)  # grows each step
Direction

Add a past_key_values cache to GroupedQueryAttention. On step n only compute K/V for the new token and concatenate with the cached K/V tensors. F.scaled_dot_product_attention supports this natively with a pre-filled attn_mask. This gives a linear-time generation loop.

High No pin_memory or async data prefetching — GPU waits on CPU llm/dataloader.py
Speed

DataLoaderLite.next_batch() is called synchronously at the top of each micro-step. The .to(device) call in the training loop initiates a pageable host→device copy that cannot overlap with GPU kernel execution. On an RTX 3060 (PCIe 4.0 x16) a single 8×1024 int32 batch transfer is ~0.3 ms — but with 8 gradient accumulation steps this stalls ~2.4 ms per optimizer step, adding up to hours over a 19,000-epoch run. 

# pre_train.py:197-198 — blocking H2D transfer mid-step
x, y = train_dataloader.next_batch()
x, y = x.to(device), y.to(device)    # GPU waits here
Fix — two-step improvement
# 1. Load tokens into pinned (page-locked) memory
def load_tokens(filename):
    npt = np.load(filename).astype(np.int32)
    t = torch.from_numpy(npt)
    return t.pin_memory()   # enables async H2D

# 2. Non-blocking transfer in the training loop
x, y = train_dataloader.next_batch()
x = x.to(device, non_blocking=True)
y = y.to(device, non_blocking=True)
High Token int32 conversion doubles tensor memory llm/dataloader.py:9
VRAM Speed

Shards are saved as uint16 (2 bytes/token) by the tokenizer, but load_tokens immediately casts to int32 (4 bytes/token) with .astype(np.int32). This materialises a full in-memory copy at double the size. On a typical 100M-token shard that wastes ~200 MB of RAM unnecessarily, and the extra copy stalls the CPU while the GPU is idle at shard boundaries. 

# dataloader.py:9
npt = np.load(filename, mmap_mode="r").astype(np.int32)  # full copy, 2× size
return torch.from_numpy(npt)
Fix
# Keep uint16, cast to int32 only when creating the batch tensor
def load_tokens(filename):
    npt = np.load(filename, mmap_mode="r")   # stays uint16, zero-copy
    return torch.from_numpy(npt.astype(np.int32))

# Or defer the cast entirely:
# return torch.frombuffer(npt, dtype=torch.int16).to(torch.int32)

Even better: keep the mmap-mode array and only cast the slice that becomes the batch (buf = self.tokens[...].to(torch.int32)), avoiding any full-shard allocation entirely.

High HellaSwag evaluation blocks the training loop scripts/pre_train.py:259–266
Speed

Every 1,000 epochs the code calls HellaSwag(model=eval_model) on the main training thread. HellaSwag has 10,000 examples; even a subset requires many O(T²) generation calls (no KV-cache, see issue #5). This adds minutes of dead time per checkpoint while the GPU sits idle between epoch steps.

Run evaluation in a background thread or separate process after saving a checkpoint. The training loop writes the checkpoint file; a worker process reads it and runs the benchmark independently without stalling epoch throughput.

import threading

def run_eval(checkpoint_path):
    # load checkpoint, run HellaSwag, log to wandb
    ...

if (epoch + 1) % 1000 == 0:
    save_checkpoint(...)
    threading.Thread(target=run_eval, args=(checkpoint_path,), daemon=True).start()

Medium RMSNorm includes a bias parameter llm/gpt.py:11
VRAM Speed

RMSNorm's defining advantage over LayerNorm is the removal of the mean-centering step and the bias term. Adding self.b back in negates this, adds extra parameters, and requires an extra addition across the full (B, T, embed_dim) tensor every forward and backward pass. Across 8 blocks with 2 norms each, this is 16 extra tensor additions per step. 

# gpt.py:11 — bias defeats the purpose of RMSNorm
self.b = nn.Parameter(torch.ones(input_shape))

def forward(self, x):
    ...
    output = (output * self.g) + self.b    # remove this
Fix
class RMSNorm(nn.Module):
    def __init__(self, input_shape, eps=1e-6):
        super().__init__()
        self.g = nn.Parameter(torch.ones(input_shape))
        self.eps = eps

    def forward(self, x):
        rms = torch.sqrt(torch.mean(x**2, dim=-1, keepdim=True) + self.eps)
        return (x / rms) * self.g   # no bias
Medium Explicit Q/K normalization — two redundant passes over attention tensors llm/gpt.py:116–121
Speed VRAM

Before the attention call, Q and K are explicitly L2-normalised using torch.norm() to compute per-head norms and then divided. torch.norm reduces over head_dim, returning a new tensor, followed by another division — two full allocations over the (B, n_head, T, head_dim) tensors. These temporary tensors add to activation memory during the backward pass and add extra kernel launches. F.scaled_dot_product_attention already handles scale via its scale parameter. 

# gpt.py:116-122 — four extra tensor ops before sdp_attention
q_norm = torch.norm(q, dim=-1, keepdim=True)
k_norm = torch.norm(k, dim=-1, keepdim=True)
q_hat = q / (q_norm + 1e-6)
k_hat = k / (k_norm + 1e-6)
factor = (self.alpha * math.sqrt(C // self.n_head)).view(1, self.n_head, 1, 1)
y = F.scaled_dot_product_attention(self.rope(q_hat * factor), self.rope(k_hat), ...)
Direction

Replace manual normalization with F.normalize(q, dim=-1) (uses a fused kernel) or, if QK-normalization is intentional, consider nn.functional.normalize which avoids the explicit norm tensor.

Medium RoPE interleave via stack+flatten allocates an unnecessary tensor llm/gpt.py:47–49

apply_rotary_pos_emb interleaves even/odd dimensions back together using torch.stack([x1_rotated, x2_rotated], dim=-1).flatten(start_dim=-2). torch.stack allocates a new tensor of shape (B, n_head, T, head_dim/2, 2) before the flatten. This allocation happens on every forward pass, twice per block (once for Q, once for K). 

# gpt.py:47-49

out[..., ::2]  = x1_rotated
out[..., 1::2] = x2_rotated
return out
Medium Synchronous checkpoint save blocks the training loop llm/checkpoint_manager.py · scripts/pre_train.py:260
Speed

save_checkpoint calls torch.save synchronously on the main thread. For a model with embed_dim=1024, num_blocks=8 the state dict is roughly 300–600 MB depending on optimizer state. Writing this to disk blocks training for several seconds every 1,000 epochs on a standard NVMe drive. 

# checkpoint_manager.py:18 — blocks training loop
torch.save(checkpoint, save_path)   # can take 2–10s for large models
Fix
import threading

def save_checkpoint_async(model, optimizer, epoch, path, filename):
    state = {
        "model_state_dict": {k: v.cpu().clone() for k, v in model.state_dict().items()},
        "optimizer_state_dict": optimizer.state_dict(),
        "epoch": epoch,
    }
    def _write():
        torch.save(state, os.path.join(path, filename))
    threading.Thread(target=_write, daemon=True).start()

Clone to CPU first (fast) then write in background — training resumes immediately.

Low Gradient clip norm 5.0 is effectively disabled scripts/pre_train.py:209
Training Stability

clip_grad_norm_(model.parameters(), 5.0) uses a max norm of 5.0. The standard for transformer LM training is 1.0. At 5.0 the clip only fires during severe gradient explosions; normal instability (e.g., loss spikes at the beginning of training) passes through unchecked. For a 12GB GPU with limited batch size, gradient instability is amplified. 

norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 5.0)
Fix
norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)

Low MLP uses plain GELU — no gating mechanism llm/gpt.py:132–137
Speed

The MLP block uses a two-layer GELU network. SwiGLU (used in LLaMA, Mistral, Qwen) replaces the plain activation with a gating projection: SiLU(xW₁) ⊙ (xW₂). SwiGLU achieves better loss at the same FLOP count. Additionally, with torch.compile enabled, SiLU fuses more cleanly than GELU in the current compiler. This is a quality improvement that also doesn't hurt throughput. 

# gpt.py:132-136 — plain GELU MLP
self.MLP = nn.Sequential(
    nn.Linear(embed_dim, 4 * embed_dim),
    nn.GELU(),
    nn.Linear(4 * embed_dim, embed_dim),
)
SwiGLU direction
class MLP(nn.Module):
    def __init__(self, embed_dim):
        super().__init__()
        hidden = int(embed_dim * 8 / 3)  # standard SwiGLU sizing
        self.gate = nn.Linear(embed_dim, hidden, bias=False)
        self.up   = nn.Linear(embed_dim, hidden, bias=False)
        self.down = nn.Linear(hidden, embed_dim, bias=False)

    def forward(self, x):
        return self.down(F.silu(self.gate(x)) * self.up(x))
Low torch.no_grad() in validation instead of inference_mode scripts/pre_train.py:232
Speed VRAM

torch.no_grad() disables gradient computation but still allows torch.autograd.grad to be called within the block. torch.inference_mode() is a strict superset that disables autograd entirely, enabling additional kernel fusions in compiled models and using less VRAM for intermediate activations. Validation never needs grad; use the stronger context. 

with torch.no_grad():           # weaker guarantee
    output = model(x)
    val_loss = loss(...)
Fix
with torch.inference_mode():    # stronger, faster
    output = model(x)
    val_loss = loss(...)
